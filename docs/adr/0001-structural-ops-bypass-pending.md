# ADR-0001：结构操作不进暂存，直接作为作业执行

日期：2026-11-22
状态：已采纳（v0.2 设计的一部分）

## 背景

v0.1 只有一条写路径：用户在面板上改仓库归属 → 写入 `pending` → 点「同步到 GitHub」→ 逐条 `updateUserListsForItem`。

v0.2 要加两类新操作：

1. **删除分类**：要么把成员移入另一个分类，要么让它们变未归类，然后 `deleteUserList`。
2. **取消 star**：`removeStar`，仓库会掉出 star 列表（GitHub 会顺带把它从所有分类里移除）。

问题：这两类操作能不能也走 `pending`，让用户统一在「同步」时写回？

## 观察

- `stage()` 只接受 `state.lists` 里存在的 list id。`deleteUserList` 一旦执行，该 id 立刻从「已知分类」里消失，因此**任何指向它的暂存记录都会在下次 `stage()` 或 `planSync()` 时被过滤掉**——「待删除的分类」这种暂存状态在现有模型里根本无法表示。
- 取消 star 不是归属变化：仓库整个从 star 集合里消失，`pending` 挂在 `state.repos[name]` 上，而这条记录本身必须被删掉。暂存一个「即将不存在的仓库」没有意义。
- 反过来，`updateUserListsForItem` 是**替换语义**，天然幂等，任何中间状态都可以安全重试——这正好是「立即执行 + 失败重试」的前提。

要支持暂存，就得给 `pending` 增加第二种操作类型（`deleteList` 等）和一套拓扑排序（先搬成员、再删分类），并且要定义「暂存了删分类后，用户又新建了同名分类」这种荒谬状态。

## 决策

**结构操作不进暂存。** 确认弹层 → 立即作为一个作业执行，作业内含必要的顺序（先清/搬成员，再删分类），逐条落盘，失败保留原状。

## 后果

- 好处：`pending` 保持单一语义（只有仓库归属），`stage()` / `planSync()` 的纯函数不变，单测不需要重写；执行过程有进度条与失败清单，和同步共用基础设施。
- 代价：结构操作没有「先看看再说」的中间态，只能靠确认弹层（显示受影响仓库数与去向）来防止误操作。因此确认文案必须具体：写「12 个仓库将变为未归类」，不写「确定吗？」。
- 未来的约束：如果哪天要做「撤销上一次删除分类」，需要的是操作日志（记录被删的 list 元数据 + 成员快照），而不是把它改成暂存。
